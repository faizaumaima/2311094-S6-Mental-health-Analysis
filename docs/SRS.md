1. Introduction
1.1 Purpose
This document specifies the requirements for the Mental Health Analysis System, a web application for recording and reviewing daily mood, stress levels, sleep hours, and personal notes. It defines the MVP for the midterm and the Beta release for the final demonstration.
1.2 Scope

MVP: Users can create, list, view, update, and delete daily well-being records through REST APIs. The system calculates basic summaries from saved records and runs locally for the midterm demonstration.

Beta: The system adds user registration, login, JWT-based authentication, two roles (User and Administrator), role-based access control (RBAC), security scopes/permissions, personal dashboards, group creation and management, group member management, member-level permissions (Create, Edit/Update, and Assign), an administrator dashboard, and deployment.

Out of scope: AI/ML, NLP, LLMs, automated diagnosis, risk prediction, and crisis detection.

2. Overall description
2.1 System context

The application has three main parts:

- Frontend: React with TypeScript, providing forms, personal dashboards, group management interfaces, and an admin dashboard.
- Backend: FastAPI with Python, handling REST APIs, validation, calculations, authentication, and permission checks.
- Database: Stores user accounts, well-being records, groups, group memberships, and application permissions.

The frontend sends HTTP requests to the backend. The backend validates requests, authenticates users, checks their roles and permissions where required, reads or updates the database, and returns JSON responses.

The backend is responsible for enforcing all access restrictions. Frontend controls alone must not be treated as security.
2.2 Users and roles

| Role | Release | Description |
|---|---|---|
| Demo user | MVP | Uses the basic well-being record CRUD features in the local demonstration. |
| Guest | Beta | Can register, log in, and access public API documentation and health information. |
| User | Beta | Manages personal records, views personal summaries, and participates in groups. |
| Administrator | Beta | Manages user accounts, oversees groups, and accesses the admin dashboard. |

In the Beta release, each authenticated account has one global role: user or admin. Group members may also have specific permissions within each group. These permissions determine whether a member can create, edit/update, or assign group records.

All permissions must be enforced by the backend. A user's global role and their group-level permissions must be checked before allowing protected operations.

MVP

2. View all saved records.
3. View one record.
4. Update a record.
5. Delete a record.
6. View basic mood and stress summaries.
7. Check backend health and explore API documentation.

Beta

2. View and update personal records.
3. View a personal dashboard.
4. Create and manage groups.
5. Add and manage group members.
6. Grant and manage group-level Create, Edit/Update, and Assign permissions.

9. Assign group records to members when authorized.
10. Allow administrators to manage user accounts and oversee groups.

2.4 Constraints

- C-1: The frontend must use React with TypeScript.
- C-2: The backend must use FastAPI with Python.
- C-3: Frontend–backend communication must use REST APIs.
- C-4: Requests and responses should use JSON unless an endpoint requires another format.
- C-5: Deployment must follow the faculty's specified Vercel setup.
- C-6: The database must use the configured Supabase PostgreSQL database.
- C-7: Beta authentication and permissions must be enforced on the backend.
- C-8: The system must not include AI, machine learning, or automated clinical assessment.
- C-9: MVP is intended for local demonstration with test data; it is not secure multi-user production access.
- C-10: Group-level permissions must control Create, Edit/Update, and Assign actions.

2.5 Assumptions

- A-1: The faculty's React + FastAPI template will be used as the starting point.
- A-2: The application will be used mainly for coursework and demonstrations, with low traffic.
- A-3: Supabase PostgreSQL will be used for persistent data storage.
- A-4: JWT authentication, roles, and security scopes will be implemented in the Beta release.
- A-5: Each authenticated account will have either the User or Administrator role.
- A-6: Group members may have different permissions depending on their access within a group.
- A-7: The backend will verify group membership and permissions before allowing protected group operations.

3.6 Validation rules

- V-1: Mood must be selected from the allowed mood values.
- V-2: Stress level must be within the defined range.
- V-3: Sleep hours must be a valid non-negative number within the allowed limit.
- V-4: Record date must be a valid date.
- V-5: Notes are optional and must follow the maximum length limit.
- V-6: Registration email must be valid and unique.
- V-7: Password must meet the defined password requirements.
- V-8: Only authenticated users may access protected Beta endpoints.
- V-9: Each account must have either the User or Administrator role.
- V-10: Group operations must verify the user's group membership.
- V-11: Create, Edit/Update, and Assign actions must require the corresponding group permission.
- V-12: A record may only be assigned to a valid member of the same group.
- V-13: Administrator-only operations must reject non-administrator users.

- Group-level permissions apply separately to each group.
- Being an Administrator does not automatically grant Create, Edit/Update, or Assign permission within every group.

- Only the group owner can add or remove members, set or update their permissions, rename the group, or delete the group.

5. Acceptance criteria
MVP
AC-01 — Create a record (FR-01)
- Given a valid record containing mood, stress level, sleep hours, and date.
- When the client submits the create request.
- Then the system saves the record and returns the created record with its ID.
AC-02 — Reject invalid data (FR-07)
- Given a record with a missing required field or an invalid stress level.
- When the client submits the request.
- Then the system returns a validation error identifying the invalid field.
AC-03 — List records (FR-02)
- Given multiple saved records.
- When the client requests the record list.
- Then the system returns the saved records in a documented order.
AC-04 — Update a record (FR-04)
- Given an existing record.
- When the client updates its stress level.
- Then the stress level changes while the other fields remain unchanged.
AC-05 — Delete a record (FR-05)
- Given an existing record.
- When the client deletes it.
- Then the system confirms deletion, and a subsequent request for that record returns 404.
AC-06 — Basic analysis (FR-09)
- Given saved mood and stress records.
- When the client requests the summary.
- Then the system returns calculations based on the stored records.
AC-07 — Health check (FR-10)
- When the client requests the health endpoint.
- Then the system returns a successful response with {"status": "ok"}.
Beta
AC-08 — Registration (FR-12, FR-13)
- Given an email that is not registered.
- When a guest submits valid registration information.
- Then an account is created with the default user role.
- If the email already exists, the system rejects the duplicate registration.
AC-09 — Login (FR-14, FR-15)
- Given a registered user with valid credentials.
- When the user logs in.
- Then the system establishes an authenticated session.
- Invalid credentials return 401 without disclosing which credential was incorrect.
AC-10 — Private records (FR-19 to FR-21)
- Given two authenticated users with separate records.
- When one user attempts to read, update, or delete the other user's record.
- Then the backend rejects the operation and does not change the record.
AC-11 — RBAC (FR-23 to FR-29)
- Given an authenticated user without administrator permissions.
- When that user requests an administrator-only endpoint.
- Then the backend returns 403.
- An administrator with the required permission can access the endpoint.
AC-12 — Group permissions (FR-30 to FR-37, including owner-only permission management in FR-32)
- Given an authenticated user.
- When the user creates a group.
- Then the system creates the group and allows authorized members to view its information.
- A member with Create permission can create a group record.
- A member with Edit/Update permission can modify an authorized group record.
- A member with Assign permission can assign a group record to another member of the same group.
- If a member lacks the required permission, the backend rejects the operation with 403 Forbidden.
AC-15 — Group owner management (FR-38 to FR-41 and FR-32)
- Given an authenticated group owner.
- When the owner adds or removes a group member.
- Then the system shall allow the operation.
- When the owner assigns or updates a member's group permissions.
- Then the system shall allow the operation.
- When the owner renames or deletes their group.
- Then the system shall allow the operation.
- If a non-owner attempts these operations, the backend shall reject the request with 403 Forbidden.
AC-13 — Security scopes (FR-25)
- Given a user who lacks the required permission for an operation.
- When that user calls the protected endpoint.
- Then the backend rejects the request even if the frontend interface is manually bypassed.
AC-14 — Deployment (NFR-15)
- Given the final application and required environment configuration.
- When the application is deployed through the approved setup.
- Then the frontend loads and its configured 
API requests reach the backend successfully.
