1. Introduction
1.1 Purpose
This document specifies the requirements for the Mental Health Analysis System, a web application for recording and reviewing daily mood, stress levels, sleep hours, and personal notes. It defines the MVP for the midterm and the Beta release for the final demonstration.
1.2 Scope
MVP: Users can create, list, view, update, and delete daily well-being records through REST APIs. The system calculates basic summaries from saved records and runs locally for the midterm demonstration.
Beta: The system adds user registration, login, authentication, role-based access control (RBAC), security scopes/permissions, personal dashboards, authorized counsellor access, and deployment.
Out of scope: AI/ML, NLP, LLMs, automated diagnosis, risk prediction, and crisis detection.

2. Overall description
2.1 System context
The application has three main parts:
- Frontend: React with TypeScript, providing forms, dashboards, and charts.
- Backend: FastAPI with Python, handling REST APIs, validation, calculations, authentication, and permissions.
- Database: Stores user accounts, well-being records, and other application data.
The frontend sends HTTP requests to the backend. The backend validates requests, checks permissions where required, reads or updates the database, and returns JSON responses.
2.2 Users and roles
Role	Release	Description
Demo user	MVP	Uses the basic well-being record CRUD features in the local demonstration.
Guest	Beta	Can register, log in, and access public API documentation and health information.
User	Beta	Manages personal records and views personal summaries.
Counsellor	Beta	Views authorized records for assigned users and manages agreed session/progress features.
Administrator	Beta	Manages accounts, roles, and counsellor assignments.
In the Beta release, each authenticated user has a global role: user, counsellor, or admin. Permissions must be enforced by the backend. A counsellor's access to a particular user's records also depends on the assignment and authorization rules.
2.3 Use cases
MVP
1. Create a well-being record.
2. View all saved records.
3. View one record.
4. Update a record.
5. Delete a record.
6. View basic mood and stress summaries.
7. Check backend health and explore API documentation.
Beta
1. Register and log in.
2. View and update personal records.
3. View a personal dashboard.
4. Access protected features according to role and permissions.
5. Allow counsellors to view authorized records of assigned users.
6. Manage agreed counselling sessions and progress notes.
7. Allow administrators to manage accounts, roles, and assignments.
2.4 Constraints
- C-1: The frontend must use React with TypeScript.
- C-2: The backend must use FastAPI with Python.
- C-3: Frontend–backend communication must use REST APIs.
- C-4: Requests and responses should use JSON unless an endpoint requires another format.
- C-5: Deployment must follow the faculty's specified Vercel setup.
- C-6: The database technology must be confirmed against the provided template and deployment requirements.
- C-7: Beta authentication and permissions must be enforced on the backend.
- C-8: The system must not include AI, machine learning, or automated clinical assessment.
- C-9: MVP is intended for local demonstration with test data; it is not secure multi-user production access.
2.5 Assumptions
- A-1: The faculty's React + FastAPI template will be used as the starting point.
- A-2: The application will be used mainly for coursework and demonstrations, with low traffic.
- A-3: A suitable database will be configured before persistent data storage is implemented.
- A-4: Authentication, roles, and security scopes will be implemented in the Beta release.
- A-5: Counsellor features may be simplified if needed to complete the essential requirements within the semester.

5. Acceptance criteria
MVP
AC-01 — Create a record (FR-01)
- Given a valid record containing mood, stress level, sleep hours, and date.
- When the client submits the create request.
- Then the system saves the record and returns the created record with its ID.
AC-02 — Reject invalid data (FR-07)
- Given a record with a missing required field or an invalid stress level.
- When the client submits the request.
- Then the system returns a validation error identifying the invalid field.
AC-03 — List records (FR-02)
- Given multiple saved records.
- When the client requests the record list.
- Then the system returns the saved records in a documented order.
AC-04 — Update a record (FR-04)
- Given an existing record.
- When the client updates its stress level.
- Then the stress level changes while the other fields remain unchanged.
AC-05 — Delete a record (FR-05)
- Given an existing record.
- When the client deletes it.
- Then the system confirms deletion, and a subsequent request for that record returns 404.
AC-06 — Basic analysis (FR-09)
- Given saved mood and stress records.
- When the client requests the summary.
- Then the system returns calculations based on the stored records.
AC-07 — Health check (FR-10)
- When the client requests the health endpoint.
- Then the system returns a successful response with {"status": "ok"}.
Beta
AC-08 — Registration (FR-12, FR-13)
- Given an email that is not registered.
- When a guest submits valid registration information.
- Then an account is created with the default user role.
- If the email already exists, the system rejects the duplicate registration.
AC-09 — Login (FR-14, FR-15)
- Given a registered user with valid credentials.
- When the user logs in.
- Then the system establishes an authenticated session.
- Invalid credentials return 401 without disclosing which credential was incorrect.
AC-10 — Private records (FR-19 to FR-21)
- Given two authenticated users with separate records.
- When one user attempts to read, update, or delete the other user's record.
- Then the backend rejects the operation and does not change the record.
AC-11 — RBAC (FR-23 to FR-29)
- Given an authenticated user without administrator permissions.
- When that user requests an administrator-only endpoint.
- Then the backend returns 403.
- An administrator with the required permission can access the endpoint.
AC-12 — Counsellor access (FR-30 to FR-32)
- Given a counsellor assigned to a user with authorized sharing.
- When the counsellor requests that user's records.
- Then the system returns only the authorized records.
- Requests for unassigned or unauthorized users' records are rejected.
AC-13 — Security scopes (FR-25)
- Given a user who lacks the required permission for an operation.
- When that user calls the protected endpoint.
- Then the backend rejects the request even if the frontend interface is manually bypassed.
AC-14 — Deployment (NFR-15)
- Given the final application and required environment configuration.
- When the application is deployed through the approved setup.
- Then the frontend loads and its configured API requests reach the backend successfully.
